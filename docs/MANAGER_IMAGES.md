# Manager photos and floor plans

In the manager dashboard, each listing has a **Photos & floor plans** section. Choose Photo or Floor plan, enter an image description, choose a JPEG/PNG, and upload. Saved images appear as thumbnails; click one to open the full image. The first photograph in the media order is the cover. Use Make cover or Earlier/Later to save a new photo order. Changes to published listings are immediately public; uploading does not change publication status.

Limits: one image per request, 10 MiB input, 24 million pixels, description up to 500 UTF-8 bytes. PDFs, SVGs, HEIC and WebP are not supported by this increment. Images are decoded and re-encoded before storage to strip embedded metadata. JPEG inputs become JPEG at quality 90; PNG inputs remain lossless PNG with transparency. The detected format, not the filename or supplied MIME type, determines the output extension. JPEG recompression is lossy and savings vary with content; use PNG for lossless plans. Original uploads are not retained. Existing PNG URLs remain valid and are not rewritten.

JPEG camera orientation is applied to pixels before metadata removal. The first EXIF APP1 primary TIFF IFD supplies orientation 1–8 (both byte orders); rotations and mirrors use integer pixel mapping without spatial interpolation. Quarter-turn orientations swap width and height while preserving pixel count. Non-identity transforms allocate an additional four-byte-per-pixel raster (up to 96 MB at the input cap), alongside decoding/encoding memory. Identity does not allocate a transform raster. Segment lengths, IFD offsets, entry counts, tag type and value counts are checked before reads; nested/thumbnail IFDs are not followed. Missing, malformed or unsupported orientation tags are ignored, and normal image decoding must still succeed. This is not a general EXIF parser. PNG EXIF orientation and colour-profile normalization remain unsupported. Previously sanitised images cannot recover metadata that was already removed; re-upload the original to apply orientation. No existing files are modified.

Use **Edit description** under any saved photo or plan to correct its label without re-uploading. Save updates the database and gallery; Cancel leaves the saved description unchanged. Failed saves preserve typed text for retry. The server enforces a 500-byte UTF-8 description limit. Descriptions are also used as image alternative text; describe the room or view rather than repeating the filename.

## API and storage

- `POST /api/v1/manager/properties/{id}/images`: authenticated multipart fields `image`, `kind` (`image` or `floor_plan`), `description`; returns saved media.
- `PUT /api/v1/manager/properties/{id}/image-order`: authenticated JSON `{ "urls": [...] }` containing every photograph exactly once; returns all media in saved order. Invalid/stale lists return 409. Non-photo media retain their relative positions.
- `PATCH /api/v1/manager/properties/{id}/image-description`: authenticated JSON `{ "url": "/photo.png", "description": "Garden entrance" }`; updates only matching photos/plans belonging to that property. Returns the saved media item. Order and publication status are unchanged.
- `/api/v1/property-images/{name}` serves an uploaded image only while its listing is published.
- `/api/v1/manager/property-images/{name}` serves previews behind manager authentication, including drafts.

Generated names are alphanumeric with `.png` or `.jpg` extensions. Both routes retain publication/authentication checks, `private, no-store` and `nosniff`. No database or frontend response-shape changes are required. Deploy the updated API to accept new JPEG URLs; no existing asset migration is needed.

New uploads larger than 480px on their longest edge also generate a thumbnail after orientation correction. Integer area averaging visits each source pixel once (O(source pixels)) and averages premultiplied channels to avoid transparent-colour fringes. Dimensions preserve aspect ratio to the nearest pixel, with a minimum one-pixel axis; small images are not enlarged or duplicated. This is box averaging in encoded colour space, not a linear-light or Lanczos filter. The thumbnail raster uses at most 480×480×8 bytes, in addition to existing decode/encode buffers. JPEG thumbnails use quality 85; PNG thumbnails preserve alpha.

Request `?size=thumbnail` on either image route for the lightweight version. Authorization/publication checks use the canonical full-image URL before resolving the derivative. Unknown nonempty sizes return 400; no arbitrary-size generation occurs on requests. Derivatives are stored as `{stem}.thumb.{extension}` and cannot be addressed directly through the public filename pattern. Missing derivatives fall back to the existing full image, so older uploads remain usable without backfill. Other storage errors remain errors. The manager media-library thumbnails use this option; opening a thumbnail still loads the full image. External image URLs are unchanged. Portfolio cover images and public property galleries are not yet switched to derivatives.

Both files are written before attaching the image to the database and are removed on normal write/attachment failure. This is not a filesystem/database transaction: crash reconciliation and uncertain database-commit recovery remain open. No original files are rewritten and no eager backfill runs. Deploy the API before relying on reduced thumbnail transfer sizes; an older API may ignore the query and return the full image.

Files live under `MEDIA_SOURCE_DIR/images`, defaulting to `.data/uploads/images` relative to the API working directory. Preserve this directory across restarts and deployments; back it up alongside the database. No image-specific schema migration or new dependency is required. Do not expose this directory as a public static directory: the API enforces draft privacy.

Remaining work: image deletion, bulk uploads, multiple responsive derivative sizes, object storage, and periodic reconciliation for files orphaned by crashes or manual database changes. If database attachment fails during a normal upload, the API removes the newly written files. Reordering and publication use existing manager permissions, not per-listing ownership.

Verification covers image sanitization, authenticated upload/preview, public draft denial, cleanup after attachment failure, persisted database ordering and duplicate-order rejection, and frontend upload/order callbacks. Browser-native file selection and visual layout still need manual QA.
